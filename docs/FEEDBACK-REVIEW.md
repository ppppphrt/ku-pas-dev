# Feedback และการเตรียมตัวอย่างที่ผ่านการตรวจ

ผู้ใช้เปิด “แสดงความคิดเห็นต่อคำตอบนี้” เลือกประเภทและให้เหตุผล ต้องยินยอมก่อนเก็บคำถาม คำตอบ บริบทที่เกี่ยวข้อง และ feedback มีความยินยอมสำหรับเตรียมชุดฝึก/ประเมินแยกต่างหากและไม่เลือกให้อัตโนมัติ ข้อความที่ไม่มี feedback ไม่ถูกบันทึกเป็นประวัติสนทนาในฐาน feedback

Backend ออก receipt ลงลายเซ็นจากข้อความและคำตอบจริง พร้อมเวอร์ชันข้อมูล โมเดล prompt และหลักฐานที่ค้นพบ อายุ 7 วัน จึงไม่รับคำตอบต้นฉบับที่ browser แก้เอง การส่งซ้ำด้วย receipt เดิมไม่สร้างรายการซ้ำ ทุก rating รวมถึงคำชมเข้าสถานะ pending

## ใช้งานบน Vercel

ฐาน PostgreSQL ชื่อ `ku-pas-feedback` ผ่าน Neon แผน Free ภูมิภาค iad1 เชื่อมเฉพาะ Production และปิด Neon Auth/Realtime ใช้ `POSTGRES_URL` หรือ `DATABASE_URL` ที่ integration เพิ่มให้ หรือตั้ง `FEEDBACK_DATABASE_URL` โดยตรง

เพิ่ม server-only Secrets อีกสองค่าแยกกัน ความยาวอย่างน้อย 32 ตัวอักษร:

- `FEEDBACK_SIGNING_SECRET`: ใช้ลงลายเซ็น receipt ห้ามนำไปใช้เป็นรหัสผู้ตรวจ
- `FEEDBACK_REVIEW_TOKEN`: รหัสผู้ตรวจ ใช้เฉพาะหน้าตรวจและ API ที่ป้องกันไว้ ห้ามใส่ในตัวแปร `VITE_` หรือ URL

สำเนา secret สำหรับเจ้าของเครื่องเก็บใน `backend/.local/feedback-production-signing.secret` และ `backend/.local/feedback-production-review.secret` ซึ่งไม่เข้า Git และกำหนดสิทธิ์ 600 ห้ามเผยแพร่ไฟล์เหล่านี้ หากเปลี่ยน signing secret receipt เก่าจะใช้ไม่ได้ หากเปลี่ยน review token ผู้ตรวจต้องใช้รหัสใหม่

Redeploy หลังเชื่อมฐานและตั้ง Secrets `/api/feedback/config` ต้องตอบ `enabled: true, automatic_training: false` การเริ่มระบบสร้างเฉพาะตาราง `chat_feedback`, `chat_feedback_reviews` และ index ที่ใช้ ไม่แก้ catalog/GE หรือฐานนักศึกษา Production ไม่ใช้ SQLite ชั่วคราว หากตั้งค่าไม่ครบหรือฐานไม่พร้อม จะไม่มีปุ่มส่ง feedback และแชทยังใช้งานได้

## หน้าผู้ตรวจ

เปิด `/feedback/review` ใส่รหัสผู้ตรวจ รหัสเก็บในหน่วยความจำของหน้าและส่งผ่าน header เท่านั้น ไม่เก็บใน browser storage สามารถดูต้นฉบับ เวอร์ชันข้อมูล หลักฐาน และประวัติการตรวจย้อนหลังได้

ก่อนอนุมัติ ต้อง:

1. แก้คำถาม/บริบทสำหรับตัวอย่างและคำตอบที่ควรเป็น ลบข้อมูลส่วนตัวออกจากทั้งสองส่วน ไม่เพียงลบจากคำตอบ
2. ตรวจข้อเท็จจริงกับข้อมูลและเวอร์ชันต้นทาง หากเป็นปัญหา retrieval/ข้อมูล ต้องแก้ระบบหรือข้อมูลแทนการสอนข้อเท็จจริงที่ผิดให้โมเดล
3. ระบุชื่อผู้ตรวจ เหตุผล แหล่งอ้างอิง และยืนยันการตรวจแหล่งข้อมูลกับความเป็นส่วนตัว

การอนุมัติไม่เปลี่ยนฐานความรู้หรือฝึกโมเดลอัตโนมัติ สามารถเปลี่ยนผลเป็น rejected เพื่อกันตัวอย่างออกจากการส่งออกรอบถัดไป การแก้ผลตรวจใช้ optimistic version check หากผู้ตรวจอื่นเปลี่ยนรายการไปแล้วจะปฏิเสธด้วย 409 และต้องโหลดใหม่ ประวัติผลตรวจแต่ละครั้งเก็บแยกและไม่ถูกเขียนทับ

## ส่งออก

ดาวน์โหลด JSONL ชุด train/eval จากหน้าตรวจ ส่งออกเฉพาะ approved + ยินยอมฝึก/ประเมิน + ผ่านสองการตรวจ ใช้เฉพาะคำถาม/บริบทและคำตอบที่ผู้ตรวจแก้แล้ว ไม่แนบ raw history หรือข้อความ feedback อัตโนมัติ

กำหนด split ประมาณ 80/20 ต่อกลุ่มบทสนทนา ทุก turn ของบทสนทนาเดียวกันอยู่ชุดเดียวกัน และกัน prompt ที่ตรงกันใน eval ออกจาก train ห้ามใช้ชุด eval มาสอนโมเดลหรือปรับจนจำชุดทดสอบ ควรเพิ่มชุดทดสอบอิสระที่ผู้ดูแลเตรียมเองด้วย เพราะการจัดกลุ่มนี้ไม่รับประกันว่า paraphrase ทุกคู่จะถูกแยกได้

ระบบนี้ยังไม่ฝึกหรือ deploy โมเดลรุ่นใหม่ ขั้นต่อไปคือคัดคุณภาพตัวอย่าง เปรียบเทียบกับ baseline แล้วจึงฝึกเป็นรุ่นและประเมินก่อนเปลี่ยนโมเดลจริง การกด checkbox ไม่ใช่การรับรองความถูกต้องอัตโนมัติ ผู้ตรวจยังต้องตรวจอย่างจริงจัง

## Local และการทดสอบ

Local ใช้ SQLite ที่ `backend/.local/feedback.sqlite` พร้อมสร้าง signing/review keys แยกใน `.local` หากไม่ตั้ง PostgreSQL หน้า local ใช้ `backend/.local/feedback-review.secret` ไม่ใช่รหัส Production

ทดสอบ: `cd backend && ../.venv/bin/pytest tests/test_feedback.py -q` และ `cd frontend && pnpm test` ครอบคลุม consent, signed evidence, expiry/tampering, private review API, approval gates, training consent, concurrent review, audit, persistence, hold-out และ export ชุดที่แก้แล้ว
